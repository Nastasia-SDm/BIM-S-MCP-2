# BIM-S MCP Server №2

Отдельный MCP stdio-сервер для чтения 2D-документации Revit. C# / .NET 10 / ModelContextProtocol 2.2.0. Работает через общий `BIMS_REVIT_BRIDGE`; напрямую Revit API из процесса MCP не вызывает.

Реализованы **ровно четыре tools**:

- `revit-documentation-ping`
- `get-documentation-elements`
- `create-documentation-elements-report`
- `get-documentation`

`get-documentation-elements` получает существующим reader полный граф и его системные параметры, сохраняя один JSON. `get-documentation` добавляет HTML из этого JSON. Нет LLM, summary, worker и наблюдения. MCP-1, generic bridge и BimSAgent при объединении не изменены.

## Сборка и проверка

```powershell
dotnet build .\BIM-S_MCP-Server-2\BIM-S_MCP-Server-2.csproj
dotnet run --project .\tests\Mcp2.Tests.csproj
```

`bridge/Bridge.Compile.csproj` проверяет расширение на установленной RevitAPI.dll 2024 и C# 7.3 / net48. Это проверочная библиотека исходников существующего add-in, не отдельный bridge для развёртывания. Её DLL не устанавливать в Revit.

Тесты сохраняют фикстуры в `artifacts/tests/<run-id>` внутри проекта. Пройдены 58 проверок: четыре публичных tool, отсутствие прежних имён, один поиск графа, композиция, ошибки этапов и сохранение сессии. Существующая DLL MCP-1 запускается отдельно: проверяются восемь прежних tools и валидация параметров. Данные документации проверяются на фикстурах, а не живом документе. Пересборка RevitAddin при объединении не требовалась: его исходники не изменены.

Отдельная проверка уже работающего bridge, только чтение:

```powershell
dotnet run --project .\tests\Mcp2.Tests.csproj -- --live-only
```

При первоначальной реализации живой ping был успешен, сессия работала и чужая сессия отклонялась; загруженный add-in ещё не поддерживал viewGraph. При объединении tools живая проверка повторно не выполнялась. Для чтения 2D необходима загруженная версия add-in с viewGraph. Исходники bridge и загруженная DLL — разные состояния.

## Ручная последовательность

1. Вызвать `get-documentation-elements` с `{}` или фильтром области. Tool получает сессию, граф и параметры всех его объектов, сохраняет один общий JSON и возвращает filePath.
2. Передать filePath в `create-documentation-elements-report` для HTML без обращения к Revit.

Либо вызвать `get-documentation` с теми же аргументами: он выполняет оба этапа и возвращает jsonPath/htmlPath. При partial сохраняет JSON с диагностикой и останавливается перед HTML.

Пример аргументов `get-documentation-elements` или `get-documentation` для выбранного листа:

```json
{"scope":"sheets","sheetIds":[12345]}
```

`scope=document` — без фильтров; `scope=sheets` — только `sheetIds`; `scope=views` — только `viewIds`. documentSession необязателен на входе; если передан, документ фиксируется этой сессией. Между внутренними этапами сессия передаётся обязательно. Неявного фильтра по активному виду нет.

Прежние обработчики сохранены. `DocumentationPipeline` использует один существующий viewGraph, уже содержащий листы, виды, размещения и аннотации, затем только пакеты elementParameters по полученным ID. Пользователю больше не нужно передавать discoveryResults или вручную собирать ID. Повторного поиска sheets/views нет.

## Результаты

Рабочий каталог задан централизованно в `ReportFiles.DefaultRoot`:

`D:\BIM-S-MCP-2_Отчеты_Версии модели`

JSON содержит граф, специализированные свойства, исходные строки параметров bridge, охват, время, сессию и диагностику. HTML — автономный аналитический отчёт в стиле MCP-1, созданный только из JSON. Это не графический экспорт листа. `partial` заметно отмечается; при полной ошибке параметров новый снимок не создаётся. Имена уникальны, запись атомарна, предыдущие снимки не перезаписываются.

Поддерживаются только встроенные параметры существующего bridge. Фактическая видимость аннотаций на печати не вычисляется; отбор выполняется по владельцу-виду. Неразмещённость в отчёте относится к выбранной области. Сессия не является номером ревизии; сбор не атомарен между запросами.
